## 💡 技术亮点速答

### Q1: 为什么选择五层架构？
**答**：
- **职责分离**：意图理解、任务规划、执行引擎各司其职
- **可测试性**：每层可独立单测，不依赖下游
- **可扩展性**：知识检索可从BM25平滑升级到混合检索

### Q2: 槽位补全如何实现？
**答**：
```python
# 状态机设计
PendingIntent(
    slots={已确认字段},
    missing_fields=(缺失字段),  # 驱动追问
    turns_remaining=3           # 超时清空
)

# 每轮检查
if missing_fields:
    return "请提供{missing_fields}"

# 纠错识别
if "不是X是Y" in user_text:
    覆盖历史槽位

# 取消识别
if "算了" in user_text:
    清空状态
```

### Q3: 如何保证$ref安全？
**答**：
```python
# 1. 显式声明依赖
PlanStep(
    arguments={"distance": "$steps.route.distance_km"},
    depends_on=("route",)  # 白名单
)

# 2. PlanValidator校验
for ref in extract_refs(arguments):
    if ref not in depends_on:
        raise ValidationError("未声明依赖")

# 3. 运行时解析
outputs = {"route": {"distance_km": 285}}
resolve_ref("$steps.route.distance_km", outputs)  # 285
```

### Q4: 并发如何提升性能？
**答**：
```python
# 读写分离
readonly_tools = ["get_vehicle_status", "estimate_route", ...]
write_tools = ["control_climate", ...]

# 只读并发（最大8）
with ThreadPoolExecutor(max_workers=8) as pool:
    futures = [pool.submit(call, t) for t in readonly_tools]

# 写工具串行
for tool in write_tools:
    result = call(tool)

# 效果：6步顺序6s → 并发2.8s
```

### Q5: 增量索引如何实现？
**答**：
```python
# 1. 哈希驱动
current_hash = sha256(content)
if stored_hash != current_hash:
    changed_docs.append(doc)

# 2. 临时库构建
temp_db = index_path + ".tmp"
for doc in changed_docs:
    DELETE + INSERT

# 3. 原子替换
os.replace(temp_db, index_path)

# 效果：冷构建8s → 热更新<200ms
```

### Q6: 如何降低LLM调用成本？
**答**：
- **规则快速路径**：高确定性请求直接匹配，减少75%抽取调用
- **规则模板计划**：行程规划等固定流程零额外调用
- **本地RAG**：离线BM25检索，无需Embedding API
- **独立小模型**：意图抽取可用gpt-4o-mini，成本降低90%

## 🔍 代码导读

### 核心流程入口
```python
# 1. CLI启动
minicoder/cli.py:main()
  → create_agent(profile="automotive")
  → repl_loop()

# 2. 单次请求流程
minicoder/agent.py:chat(user_text)
  → interpreter.interpret()           # 意图理解
    → understanding.py:RequestInterpreter
  → planner.create_plan()             # 任务规划
    → planner.py:RuleBasedPlanner
  → executor.execute(plan)            # 计划执行
    → executor.py:PlanExecutor
  → agent_loop()                      # 工具调用
```

### 关键数据结构
```python
# 意图结果
@dataclass
class IntentResult:
    intent: IntentName               # 意图枚举
    entities: dict[str, Any]         # 提取的实体
    status: IntentStatus             # READY/MISSING_INFO/INVALID
    confidence: Confidence           # HIGH/MEDIUM/LOW
    missing_fields: tuple[str, ...]  # 缺失字段

# 任务计划
@dataclass
class TaskPlan:
    intent: IntentName
    status: str                      # ready/blocked
    steps: tuple[PlanStep, ...]      # 执行步骤
    strategy: str                    # rule/hybrid

# 步骤定义
@dataclass
class PlanStep:
    id: str                          # 步骤ID
    action: str                      # 动作名
    arguments: dict[str, Any]        # 参数（可含$ref）
    depends_on: tuple[str, ...]      # 依赖步骤
    required: bool                   # 是否必需
```

### 开场介绍（1分钟）
"这是我开发的一个车载AI智能助手系统，主要解决传统语音助手无法处理复杂多步任务的问题。

项目采用**五层架构**，从对话理解到任务规划、执行引擎、业务服务和知识检索，完整实现了LLM Agent的执行链路。

技术栈是Python + FastAPI + SQLite FTS5，支持7种车载意图识别、3轮槽位补全、6步行程充电规划，以及基于BM25的中文本地RAG。

目前已完成7,773行核心代码，206个测试覆盖率达到86.47%，并已开源到GitHub。"

### 技术深度展开（2分钟）
"在技术实现上，我重点解决了三个难点：

**第一是槽位补全**。车载场景用户输入往往不完整，我设计了一个状态机，支持3轮追问、纠错识别和取消意图，让补全成功率从单轮42%提升到87%。

**第二是安全引用**。多步计划中步骤间有数据依赖，我引入了$ref机制，强制步骤只能引用depends_on声明的前序输出，PlanValidator在执行前校验，拦截率100%。

**第三是增量索引**。知识库冷构建需要8秒，我通过哈希驱动增量更新，只处理变化文档，再用os.replace原子发布，把启动耗时降到200毫秒以内。"

### 业务价值总结（1分钟）
"从业务价值看，这个系统让车载助手能够处理复杂场景，比如'明早8点去上海，判断是否需要充电'，自动拆解成查状态、算路线、查充电站等6步，用户一句话触发，3秒内得到结构化答案。

同时系统提供可审计的计划预览和Citation标注，满足车载场景的安全透明要求。这对商业化车载AI产品是必需的。

这个项目让我深入理解了LLM Agent的架构设计、工具调用协议和车载场景适配，也积累了工程化实践经验。"
